审阅结论

这轮 Round-35 总报告 和 导航与 target-lane 责任审计 的证据很强，已经足够改变项目优先级：

当前首要瓶颈不是 World Model 精度，而是车道、闸口和局部路径选择被错误的外部 target-lane 规则强约束，同时网络自身的自主选道能力尚不可靠。

可以批准启动网络内部候选车道、候选路径生成与选择原型。但我不同意把“换一个障碍感知的外部 target-lane 规则”变成生产方案，它只能作为诊断上界。

一、本轮最重要的发现
1. 当前导航确实是“道路级导航 + 外部车道级答案”的混合系统

当前 nav 有 11 维，包括：

前方两个路线节点的相对坐标
直行/左转/右转命令
路线完成度


它属于道路级路线信息，这是合理的。route_world 也属于道路级路线折线。

但是代码中的 select_target_lane() 会在网络外部，根据：

当前路段参考车道集合
下一路段参考车道集合
ego当前车道
lane id与续接几何


强制选出一条唯一 target lane。该规则明确不检查障碍物或路径可行性。

随后，围绕这条规则选出的车道，又计算：

横向误差
航向误差
近远曲率
左右道路余量
是否需要换道
到车道末端距离
route关联置信度


并编码成一个网络强消费的 target-lane token。

所以当前系统实质上是：

道路级导航
→ 外部规则选唯一车道
→ 网络主要学习跟随或修正这条车道


而不是：

道路级导航
→ 网络自主选车道、闸口及变道时机

2. 收费站失败的外部 target lane 全部有问题

在 10 个收费站失败 episode 中，外部规则选择的 target lane：

正确率 = 0/10


这些 target 所指向的通道被岗亭或障碍占据，同时同一道路上存在空闲替代通道。失败集中在“外部 target 错误 + Policy 跟随错误先验”。

这已经直接证明：

外部 target-lane 规则不是一个无害辅助条件，而是当前收费站失败的缺陷源之一。

3. Target lane 和道路级导航都被网络强烈消费

将 target lane 替换成左侧相邻车道后，动作和六步计划立即发生大幅变化：

Policy动作最大变化中位数：约1.35m
计划最大变化中位数：约1.94m
车道序列变化率：约71%


并且有 3 个 merge 失败 episode 转为成功，没有成功 episode 因此变为失败。

单独改变道路级路线和转弯命令，同样立即显著改变动作和计划；这说明道路级 navigation 并非被忽略。

结论是：

道路级route：强消费
外部target lane：也强消费


两套条件同时作用，但 target lane 是更具体、更直接的车道级强先验。

4. 去除 target-lane token 后，网络有选道行为，但不可靠

去掉 target-lane token 或 target identity 后，网络仍会主动变道，说明网络内部不是完全没有车道选择能力。

而且收费站计划进入阻塞车道的比例明显下降，例如某些 episode 从约：

0.52 → 0.17


甚至下降到零。

但收费站：

10/10仍然没有成功


这说明：

网络内部已有车道选择的“行为雏形”，但缺少明确的候选生成、候选比较和稳定换道执行能力。

不能简单删除 target-lane token，然后期待网络自动学会完整选道。

5. Merge 与收费站并不是同一个问题

收费站主要是：

外部target lane错误
+
网络跟随错误先验
+
即使交换target也没有完成变道


Merge 则是：

外部target基本合法
但Policy生成的横向路径压线或越界


7 个 merge 失败中，target lane 被判定为合法，但路径横向几何错误。交换 target 后其中 3 个 episode 转为成功，说明 target 选择的任意 tie-break 会影响结果，但直接故障仍是路径生成。

因此新结构必须同时解决：

收费站的通道、闸口选择；
merge 的车道锚定路径生成；
变道应在多远之前启动； 4.选中可行通道后能否生成并完成连续路径。
二、对 Coding Agent 建议的评价
1. 动态 Hooks 工作做得好

本轮新增了：

40 项输入记录；
351 项网络消费统计；
17 项 rollout 数据；
11 项 LQR reference 数据；
effective rank、有效槽位比例、激活范数、饱和比例；
checkpoint、配置和参数哈希。

默认关闭时前向逐位一致，不消耗随机数，不改变 checkpoint 或参数哈希。

这符合我们之前提出的要求，应成为后续所有新模块的强制规范。

目前仅剩的重要缺口是：

ego-motion warp前后的OD/LD anchor记录


另外，候选路径分数 hook 虽已准备好，但当前模型根本没有候选头，这恰恰证明下一步需要新结构。

2. 数据量足够启动原型

现有专家数据中约有：

收费站：455
merge：441
路口：906
普通道路：907


足以支持第一轮候选覆盖、模仿学习和分层验证。

真正缺少的是：

带完整新字段的独立验证集；
Policy 失败状态数据； -显式静态对象 slots； -候选路径几何和可行性标签。

所以 Coding Agent 提出的离线提取约 2,002 个 episode 候选几何和静态对象 slots，应批准先行。

3. “障碍感知 target-lane 规则”只能作为诊断臂

Coding Agent 建议增加一个会绕开障碍物的 target-lane 规则，用来测试“如果 target lane 正确，现有 Policy 的闭环天花板是多少”。这个实验有价值。

但必须锁定：

默认关闭
只作诊断
不进入生产
不作为新baseline


因为它仍然是在外部替网络完成：

闸口选择
车道选择
避障方向选择


唯一目的应是回答：

如果把正确车道答案喂给现有 Policy，它最多能提升多少？

若即使给正确 target，收费站还是全部失败，说明主要问题还包括：

变道启动太迟
横向路径能力不足
路径速度协调不足


本轮 swap target 后收费站 10/10 仍失败，已经提示“正确 target 是必要但不充分的”。

三、下一步优先级
现在不应继续单线优化 World Model

当前证据链已经形成：

动作条件化V2：
改善接口约10%–12%
但success不提升

路径审计：
收费站和merge总有可行候选

导航审计：
收费站外部target规则0/10正确

无target token：
有自主行为但不可靠


因此，当前闭环第一杠杆是：

将车道、闸口和路径选择从外部规则迁回网络内部。

World Model 保留，但降为第二主线，等待新动作与新规划表示稳定后再适配。

四、批准启动网络内部候选路径原型

我批准 Coding Agent 启动 WP3，但建议正式命名为：

Network-Internal Lane and Path Selection


避免继续使用过多简称。

输入

外部只允许提供：

道路级route/nav
当前和下一路段的可见车道集合
各车道几何与拓扑连接
静态对象slots
动态对象slots
ego状态


禁止提供：

selected_lane
selected_gate
best_candidate
recommended_lane_change_direction

候选集

至少包括：

保持当前车道
当前车道中心线续接
左侧连接车道
右侧连接车道
route continuation连接车道
收费站可见闸口对应车道


需要强调：

候选生成可以使用客观地图拓扑，但是不能由规则过滤成“最佳候选”。

所有合法、可见、与道路级 route 拓扑兼容的候选都应保留给网络评分。

横向路径表示

每条候选以对应车道中心线为锚，网络预测残差：

near curvature residual
middle curvature residual
far curvature residual


而不是从零生成任意路径。

好处：

Merge 至少可以保持本车道中心线续接； -收费站可以自然获得多个闸口候选； -网络仍然可以通过曲率残差绕障和修正； -更容易保证路径连续、有界和可执行。

最新候选覆盖实验已经证明，失败样本的最佳候选全部是车道锚定路径，这支持该设计。

候选评分

每条候选的评分输入应包括：

道路级route一致性
车道拓扑连接
静态对象最小余量
动态对象TTC
道路边界余量
路径曲率及变化率
完成变道所需距离
当前速度
候选纵向速度/进度


客观几何由确定性函数计算，网络负责最终评分。

纵向规划

每条横向候选独立输出：

未来6步沿路径进度 s(t)
或速度 v(t)


而不是共享同一个 ds。

这样可实现：

左侧闸口候选：路径安全，可保持一定速度
中间岗亭候选：路径碰撞，应减速或低评分
右侧闸口候选：可行但需提前变道，速度需适配

五、Target-lane token 的迁移策略

不能立刻删除，它已经被现有模型强烈依赖。

建议三阶段迁移：

第一阶段：教师辅助

保留现有 target-lane token，但只作为训练辅助：

旧target token
+ 新候选lane tokens


并对旧 token 使用随机 dropout。

第二阶段：降低依赖

dropout 逐步增加：

30% → 60% → 90%


同时监督候选评分和路径生成。

第三阶段：部署删除

训练时仍可用专家未来轨迹提取多正例监督，但部署只输入：

道路级route
候选车道客观属性
场景对象


外部 target lane 不再出现。

六、训练标签不能使用唯一最佳车道

收费站往往存在多个安全闸口。若强制唯一标签，网络会学到不必要的偏好。

应使用多正例：

可碰撞：负例
越界：负例
与route不连接：负例

安全且连接route：
全部正例


选择损失可以是：

多标签分类
+
候选排序
+
轨迹回归
+
纵向速度监督


专家实际选择只作为正例之一，不应成为唯一正确答案。

七、进入训练前的门
数据门
收费站候选覆盖 >=95%
merge候选覆盖 >=95%
路口候选覆盖 >=95%
普通道路候选覆盖 >=99%

网络响应门
改变道路级route → 候选评分应变化
改变静态对象位置 → 相关候选评分应变化
移除旧target token → 仍能生成合理候选
左右镜像 → 候选和曲率镜像一致

选择门
安全可行候选 top-1 >=70%
安全可行候选 top-3 >=95%
收费站错误闸口减少 >=50%
merge路径越界减少 >=50%
路口错误入口减少 >=50%

闭环门

第一轮应达到：

success >=0.64
off-road <=0.10
collision <=0.08
timeout <=0.10
route completion不下降


否则不进入 DAgger、MoE 或 RL。

八、World Model 后续位置

新 Policy 表示稳定后，World Model 再按新状态与动作表示重训：

横向曲率路径
+
路径条件化速度/进度
+
显式OD/LD anchors
+
ego-motion坐标补偿
+
学习型残差动力学


然后执行已达成共识的交替训练：

World Model更新步：
真实状态 + 实际执行动作 → 真实下一状态

Policy更新步：
真实状态 → 专家动作
预测状态 → 与真实未来状态保持决策一致


DAgger 同时提供：

Policy标签：专家应做什么
World Model标签：实际执行后发生了什么

最终裁决

批准开工网络内部候选车道与路径选择原型。

同时锁定：

障碍感知外部 target 规则只作诊断上界，不进入生产； 2.道路级导航继续由环境提供； 3.车道、闸口、变道时机和最终候选选择必须由网络完成； 4.merge 首先保证本车道中心线续接； 5.收费站候选必须覆盖所有可见且与 route 连接的闸口； 6.旧 target-lane token 逐步 dropout，不直接删除； 7.现有 Policy 保留为默认关闭时的 fallback； 8.数据提取和 hooks 先行，训练后置； 9.World Model 暂不扩容，待新规划表示稳定后再适配； 10.未过闭环门，不启动 DAgger、MoE 或 RL。

这轮已经把根因从“网络可能不会选车道”推进到了更明确的事实：

当前外部 target-lane 规则在收费站失败集上就是错误源，而网络虽然存在自主变道行为，却缺乏可靠的候选生成、车道选择和连续路径执行能力。

现在继续修外部规则只能获得短期止损。要真正超过 IDM+Pure Pursuit，应把这部分能力重新建回 Policy。
